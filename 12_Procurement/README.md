# 13_Procurement — for the buying side

NOT legal advice and NOT a curriculum. One document for procurement functions, category teams, and the
business owners who run supplier evaluations — with their own legal function reviewing before anything reaches
a supplier.

## Why it is separate from folder 10

MZ-LAW-002 (folder 10) is written for the lawyer drafting the agreement. MZ-PRC-001 is written for the person
running the evaluation: requirement language for an RFP, a structured demonstration day, a scoring scheme,
vendor-response red flags, and the terms to carry into the contract. Different reader, different artefact,
overlapping content by design. A procurement team that reads MZ-LAW-002 will get drafting concepts without an
evaluation method; a lawyer who reads MZ-PRC-001 will get an evaluation method without drafting depth. Send
both when both functions are in the room.

## MZ-PRC-001 — Procuring Agentic Systems (6 pp)

- **Sequencing.** The commonest failure is not choosing the wrong supplier; it is an evaluation that starts with
  capability and ends with capability, with the risk function's questions arriving too late to answer. Ask the
  second meeting's questions in the first.
- **Requirement language.** A four-row do-not-write / write-instead table. Outcome plus demonstration, never
  mechanism — a requirement naming an architecture can be satisfied literally while the property fails, and is
  obsolete at the first platform change. Includes the public-procurement alignment: outcome-plus-demonstration is
  technology-neutral by construction, which usually sits better with objectivity and non-discrimination
  obligations than a specification naming an architecture. Offered as context to verify, not as a legal position.
- **The demonstration day.** Nine items, half a day, against a working environment. Give the list to the supplier
  in advance — the object is not ambush, and a supplier who prepares well is demonstrating the capability being
  assessed. Run it with someone from the second line present.
- **Scoring.** Three verdicts, no partial credit, nothing for a roadmap entry.
- **Four traps and the phrases that signal them**, each with the one follow-up question to ask — plus "instantly
  reconfigurable, with no release cycle" and any adherence percentage quoted for a rule that admits no exception.
- **Terms to carry forward.** Eight concepts, with the demonstration behind each.

## Discipline

- The document states no law and no procedural rule, and says so twice. Public bodies operate under obligations
  it does not describe. It is drafting material for counsel to rework, not a template to issue.
- Every requirement is an outcome satisfiable by any construction. If a requirement can only be met by buying
  something specific, it is badly drafted — that rule is stated in the document's own interest declaration and
  should survive any edit.
- The "no source code, no model weights, no training data" property is the commercial unlock, not a technical
  footnote: it is what makes a demonstration right survive the trade-secret objection that defeats a
  conventional audit right.
- Advise buyers to run the demonstration day internally, against a system they already operate, before running
  it against a supplier. It calibrates expectations and prevents demanding a standard outside that is not met
  inside.
